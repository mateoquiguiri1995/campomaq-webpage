# Run Tracking

Bronze ETL executions write a record to `platform.etl_runs` in Supabase.

## Run ID Format

```
YYYYMMDD_HHMMSS   →   e.g. 20260515_100000
```

Generated by `campomaq_etl.common.run_tracking.generate_run_id()`.
Unique per second. For historical runs processing multiple chunks, each chunk gets its own run ID.

## Source Row Hash

SHA-256 of concatenated key business field values, truncated to 16 hex characters.

```python
# Example: product row
fields = [str(row["product_code"]), str(row["product_name"]), str(row["price"]), str(row["stock"])]
hash = sha256("|".join(fields).encode()).hexdigest()[:16]
```

Field selection per entity is defined in `campomaq_etl.bronze.schemas`. Finalized in Week 2 after PK discovery.

## etl_runs Table

```sql
CREATE TABLE IF NOT EXISTS platform.etl_runs (
  run_id        TEXT        NOT NULL,
  job_name      TEXT        NOT NULL,
  started_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  finished_at   TIMESTAMPTZ,
  status        TEXT        NOT NULL CHECK (status IN ('running','success','failed')),
  rows_read     INTEGER,
  rows_written  INTEGER,
  data_start_at TIMESTAMPTZ,
  data_end_at   TIMESTAMPTZ,
  error_message TEXT,
  PRIMARY KEY (run_id, job_name)
);
```

`job_name` values:
- `bronze_ingestion`

Silver and Gold refreshes run inside Supabase Cron and are tracked separately in
`cron.job_run_details` as `silver-clients-daily` and `gold-clients-refresh`.

## Run Lifecycle

```python
run_id = generate_run_id()
start_run(job_name, run_id)           # status = 'running'
try:
    rows_read, rows_written = do_work()
    complete_run(job_name, run_id, rows_read, rows_written)  # status = 'success'
except Exception as e:
    fail_run(job_name, run_id, str(e))   # status = 'failed'
    raise
```

## Incremental Lookback

In incremental mode, the script looks up the last successful run for its job name:

```sql
SELECT MAX(finished_at) FROM platform.etl_runs
WHERE job_name = '<job>' AND status = 'success';
```

It then reads rows from Bronze/Silver updated after `(last_success - 15 min)`. The 15-minute safety window handles clock skew and late-arriving rows.

## Retry Policy

- Supabase Cron: a failed refresh is recorded in `cron.job_run_details`; the next scheduled run tries again.
- On-prem cron: no automatic retry. Task Scheduler re-runs on next trigger.
- Bronze failures are logged in `etl_runs.error_message`.

## Idempotency Strategy

Bronze uses upserts against entity-specific conflict targets. The two
materialized client views are rebuilt by their Supabase refresh jobs; all other
Silver objects are normal views.

Historical runs split the date range into 30-day chunks, each with its own `run_id`.
